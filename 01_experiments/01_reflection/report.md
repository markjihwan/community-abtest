# 12기 중간 회고 실험 — 데이터 분석 현황 리포트

> 작성일: 2026-06-22 · 대상: 12기 빌더 · 운영진 · 분석 참여자
> 목적: 회고 실험 분석이 **지금 어디까지 왔고, 무엇을 더 해야 하며, 어떤 규칙으로 작업해야 하는지**를 누구나 빠르게 이해하도록 정리.

---

## 0. 3줄 요약 (TL;DR)

1. 회고 실험은 **6/28 시작 → 아직 데이터 0건**. 지금 나온 숫자는 *실험 결과*가 아니라 **청강생을 걷어낸 12기 베이스라인**이다.
2. 데이터에 **함정 2개**가 있다 — ① 청강생(auditor)이 섞이면 출석률이 부풀려지고, ② 스냅샷 테이블은 날짜 필터 안 하면 30~53배 중복된다. **둘 다 보정 완료.**
3. 지금 가장 급한 일은 **6/28 전에 (a) 회고 이벤트 적재 확인, (b) 회고 이전 상태 스냅샷 박제**다. 지나가면 복원 불가.

## 1. 우리가 하려는 것 (실험 한눈에)

- **실험**: 프로젝트 페이지에 "중간 회고 작성하기"를 띄우고, **전원 노출 → 회고 작성자 vs 미작성자**의 완주율 차이를 본다.
- **성격**: 무작위 A/B가 아니라 **준실험**(자기선택). 그래서 "작성자가 원래 더 성실한 사람이라서 잘한 것 아니냐"는 **선택편향**을 걷어내는 게 분석의 핵심.
- **기간**: 노출 6/28 ~ 7/5, 완주율 판정은 **시즌 종료 후**.
- **핵심 지표**: 완주율(Primary) / 4주 리텐션·이탈률(Guardrail) / 출석률(Supporting).

---

## 2. 지금까지 확인한 것 (12기 실제 수치)

**범위**: 정규 멤버 **195명**, **28~30개 프로젝트**, 시즌 **14주차 진행 중**(16주 프로그램, 전 프로젝트 active·완료 0) · 최신 스냅샷 2026-06-20 · **청강생 제외**

| 지표 | 계층 | 값 | 한 줄 해석 |
|---|---|---|---|
| 전체 출석률 | Supporting | **66.5%** | 청강생 포함 시 더 높게 잡힘(오염) |
| 4주차 리텐션 | **Guardrail** | **82.8%** | W1 169명 → W4 140명 |
| 이탈률(W1→W2+무출석) | **Guardrail** | **2.4%** | 169명 중 4명 |
| 완주율 | **Primary** | **측정 불가** | 시즌 미종료(평균 마지막 출석 9.5주차) |
| 완주 진행 프록시 | 참고 | 8주+ 도달 **147명(75%)**, 12주+ **55명(28%)** | 아직 진행 중 |

**프로젝트별(표본 크기 주의)**: 정규 인원 `n≥30`인 프로젝트는 **단 1개**(Season 12 Builder Program 35명, 38.3%). 나머지 27개는 30 미만, 대부분 4~15명 → **개별 프로젝트 단위 결론은 신중**.

## 3. 데이터에서 발견한 함정 2가지 (반드시 알 것)

### 함정 ① 청강생(auditor) 오염
- 청강생은 완주 의무가 없는 비정규 참여자인데, **정규 멤버에 섞여 출석/리텐션/이탈 지표를 왜곡**한다.
- 실측(12기): 정규 195명 **66.5%** vs 청강생 32명 **74.1%** → 청강생이 약 14%이고 출석률이 더 높아 **섞으면 위로 부풀려짐**.
- ⚠️ 함정의 핵심: **`dl_project_members.role`에는 `runner/builder/member`만 있고 `auditor`가 없다.** 즉 `dl_*` 원본 테이블로는 청강생을 못 거른다.
- ✅ 해결: 청강생 구분(`participant_type`)이 있는 **`dm_member_weekly_attendance` / `dm_project_weekly_attendance` 마트**를 쓰고 `participant_type='regular'` 필터.

### 함정 ② 스냅샷 중복 카운트
- 일부 테이블은 **매일 전체 상태를 다시 적재(snapshot)**한다. 날짜 필터 없이 `COUNT(*)` 하면 며칠치가 겹쳐 **수치가 몇십 배로 뻥튀기**된다.
- 실측: `dl_projects`는 30일치 스냅샷(292개/일) → 미필터 시 **30배**. `dm_member_weekly_attendance`는 `as_of_date` 90개 → 약 **53배**.
- ✅ 해결: snapshot 테이블은 `base_date = (SELECT MAX(base_date) ...)`, **dm_* 마트는 `as_of_date = (SELECT MAX(as_of_date) ...)`** 필터 필수. (마트는 base_date가 아니라 as_of_date를 쓰니 주의)

## 5. 주요 쿼리 설명

> 전체 SQL은 [`queries.md`](./queries.md)에 있음. 모든 쿼리 공통 필터: `as_of_date=MAX` + `participant_type='regular'` + `member_status='active'` + `cohort='12'`.

| 메트릭 | 무엇을 구하나 | 핵심 로직 (쉽게) |
|---|---|---|
| **1 / 1_1 출석률** | 멤버별·집계 출석률 | `SUM(출석세션) / SUM(전체세션)`. 청강생 빼고 정규만 |
| **1_2 프로젝트 출석률** | 프로젝트별 정규 출석률 | `dm_project` 마트의 `regular_attendance_rate` 사용 (청강생 별도 `auditor_attended_count`) |
| **2 4주 리텐션** | 초반 정착 후 4주차까지 남았나 | `1주차 출석자` 중 `4주차에도 출석한 사람` 비율 |
| **3 이탈률** | 1주차만 나오고 사라졌나 | `1주차 출석자` 중 `2주차 이후 한 번도 출석 안 한 사람` 비율 |
| **부록 청강생 점검** | 오염 규모 확인 | `participant_type`별 인원·출석률 비교 |

**왜 `dm_*` 마트를 쓰나?** 원본 `dl_project_members`로는 청강생을 못 거르기 때문(`role`에 auditor 없음). 마트는 regular/auditor를 이미 분리해 둔 "정본"이다.

## 6. 작업 가이드라인 (분석할 때 반드시 지킬 6규칙)

1. **청강생 제외**: `participant_type='regular'`. 출석/완주 관련은 `dl_project_members` 말고 **`dm_*` 마트** 사용.
2. **스냅샷 날짜 필터**: snapshot은 `base_date=MAX`, **dm 마트는 `as_of_date=MAX`**. 안 하면 30~53배 중복.
3. **모집단 먼저 고정**: "6/28 시점 active 정규 멤버". 이탈자·청강생 제외 후 분석 시작.
4. **표본 부족하면 결론 금지**: 그룹당 `n<30`이면 방향만 보는 "탐색"으로. 프로젝트 단위는 대부분 탐색 수준.
5. **인과 단정 금지**: ✗"회고가 완주를 높였다" / ✓"작성자 그룹이 완주율이 X%p 높았다". **Guardrail 훼손 시 결과 무관하게 ship 금지.**
6. **쿼리 엔진 제약**: `WITH`(CTE) 미지원 → **FROM 서브쿼리**로. `SELECT`만, `LIMIT ≤ 100`, 세미콜론 불가.

## 7. 현재 한계 / 측정 불가 (정직하게)

- **회고 실험 결과 0건** — 6/28 시작 전. 위 수치는 전부 베이스라인.
- **완주율 미측정** — 12기 전 프로젝트 진행 중(완료 0), 평균 9.5주차. 시즌 종료 후 가능.
- **new/returning 분리 불가** — 출석 마트가 12기만 커버(11·10기 각 1명). 다른 소스 필요.
- **완주 정의 미확정** — `session_submissions`는 빈 테이블. 대체 신호 확정 필요(TODO #4).
