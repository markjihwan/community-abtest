# 지환님께: 사이드바 설계서 + 백로그 피드백 (K)

> **📄 요약 ·** 사이드바 설계서·백로그에 대한 분석가(K) 피드백 — 잘 된 점, 보강 포인트, 회고 실측에서 드러난 함정. [`사이드바실험_검토리포트.md`](./사이드바실험_검토리포트.md)와 세트.

## 총평

설계 전반이 탄탄합니다! 특히 분모 정의(exposure)·인과 해석·KPI 계층 매핑이 정확합니다. 아래는 회고 1일차 실측과 플랫폼 코드 정독에서 확인한 내용을 바탕으로, **글 작성 이후 진척된 부분**과 **실전에서 드러난 함정** 위주로 정리한 것입니다.

## 잘 된 점

- **분모 = `exp_exposure`(노출), 미노출 제외**를 명시한 점. 회고에서 겪은 분모 혼선을 선제적으로 차단했습니다.
- **randomized이므로 인과 해석 가능**을 회고(준실험)와 대비해 정확히 기술했습니다.
- KPI 계층의 Playbook 매핑, sticky 해시 배정 — 실제 코드(`crc32(user_id:flag_key) % 100`)와 일치합니다.

## 보강 — 사이드바 설계서

| # | 항목 | 내용 |
| --- | --- | --- |
| 1 | **트래킹은 SDK에 이미 구현됨** | `decide()`가 `exp_exposure`(impression)를, `track()`이 conversion을 자동 전송합니다. "이벤트 적재를 새로 구축"이 아니라 **렌더 + 호출 삽입**으로 범위가 좁아집니다. 단 `track()`이 모든 이벤트를 `conversion` 고정 전송하므로, 전환율 계산 시 `event_name` 필터가 필요합니다. |
| 2 | **`session_id`·`device` 누락 위험** | 회고에서 이 두 필드가 16건 전부 누락됐습니다. 사이드바는 클릭-노출 짝·세션당 1회 노출이 분모 정확도의 핵심이라, 적재 QA(SNAV-14)에서 반드시 확인이 필요합니다. |
| 3 | **SRM 계산** | `result`보다 `analytics`의 `_srm_check`(관측 vs 균등기대 chi²)를 사용하는 편이 안전합니다. `result`의 SRM 테이블 구성이 표준 형태가 아니었습니다. |
| 4 | `page_view` | `dl_page_views`가 빈 테이블입니다. 퍼널(핵심페이지 도달)에 사용하려면 적재 확인이 필요합니다. |
| 5 | 표본/도달 | 회고 1일차 노출이 6명이었습니다. MAU 500이어도 실제 노출 도달이 관건이라, `calc_sample_size` MDE 산정 시 "며칠 내 ≥450/그룹 도달 가능 여부"도 함께 보면 좋겠습니다. |

## 보강 — 백로그(PLAT/SNAV)

| # | 항목 | 내용 |
| --- | --- | --- |
| 1 | **PLAT-1 상태 재평가** | `event_log`는 이미 작동 중입니다. 회고가 6/28부터 viewed/clicked를 적재하고 있습니다(D1 확인). Blocker 유지 시 사이드바가 불필요하게 대기할 수 있습니다. |
| 2 | **SNAV-9 범위 축소** | SDK가 노출/전환을 자동 전송하므로 "렌더 + `decide`/`track` 호출 삽입" 수준으로 추정치가 줄어들 수 있습니다. |
| 3 | **SNAV-12 중복 점검** | 대시보드 P0/P1 패널이 ExperiBase "실험 판단" 탭에 이미 구현돼 있습니다. 사이드바 config 주입만으로 가능할 수 있습니다. |
| 4 | SNAV-15 분담 | 결과 분석·판정 담당을 정해두면 좋겠습니다(회고는 트래킹 QA=지환 / 박제·설계=K으로 분담). |

## 핵심 요약

트래킹·`event_log`·대시보드가 설계서 작성 시점보다 많이 진척됐습니다(회고가 실제로 사용 중). 따라서 **새로 구축할 범위는 줄었고**, 대신 `session_id`·`device` 누락 같은 **실전 함정을 사전에 막는 것**이 중요해졌습니다.
