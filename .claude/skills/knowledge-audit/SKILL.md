name: knowledge-audit
description: 레포의 기존 지식이 맞는지 검증하거나, 새로운 지식을 해석하고 수용 여부를 판단한다.
  "이 내용 맞아?", "최신 연구랑 다른 것 같은데", "이 논문 우리한테 적용 가능해?",
  "문서 업데이트 필요한가?", "새로운 방법론 나왔는데 어떻게 봐야 해?" 등을 요청할 때 사용한다.
---

# 핵심 원칙 (autoresearch 패턴)

> **루프가 핵심이다.** 한 번의 판단으로 끝내지 않는다.
> 기준을 먼저 정하고 → 테스트하고 → 통과/폐기를 명확히 하고 → 반복한다.
> 애매하게 "참고할 만하다"로 끝내지 않는다.

---

# 모드 선택

사용자 요청에 따라 두 모드 중 하나를 선택한다:

- **Mode A: 기존 지식 검증** — 레포 문서의 내용이 실제로 맞는지 점검
- **Mode B: 새 지식 해석** — 외부 연구/방법론을 우리 환경에 적용 가능한지 판단

---

# Mode A: 기존 지식 검증 루프

## Step 1: 문서 로드
`mcp__abtest-docs__read_file`로 검증 대상 문서를 읽는다.

## Step 2: 판단 기준 먼저 정한다 (val_bpb 등가)
검증 전에 "무엇이 통과 조건인가"를 명시한다:
- 실제 운영 케이스에 적용 가능한가?
- 내부적으로 모순이 없는가?
- 전제 조건이 우리 환경(cohort 기반)에 맞는가?

기준 없이 검증하지 않는다.

## Step 3: 갭 점검 (Syneidesis)
TodoWrite로 기록한다:
- `[Gap:Assumption]` 이 지식이 전제하는 조건이 우리 환경에 실제로 성립하는가?
- `[Gap:Procedural]` 이 지식을 적용하는 절차가 문서에 빠져 있는가?
- `[Gap:Consideration]` 이 지식이 놓치고 있는 반례나 예외가 있는가?

## Step 4: 검증 루프 (반복)
검증할 지식 단위(claim)를 하나씩 꺼내서 루프를 돌린다:

```
[Claim 1]
  → 판단 기준 적용
  → Analogia: 이론이 우리 실무에 실제로 매핑되는가?
  → Epharmoge: 기술적으로 맞지만 우리 맥락에 안 맞는가?
  → 판정: PASS / FAIL / CONDITIONAL
  → FAIL이면: 수정 필요 내용 명시
  → 다음 Claim으로

[Claim 2] → 반복
...
```

**판정 기준:**

| 판정 | 의미 | 후속 조치 |
|------|------|---------|
| **PASS** | 기준 충족, 현행 유지 | 없음 |
| **FAIL** | 기준 미달, 수정 필요 | 수정안 제시 |
| **CONDITIONAL** | 조건부 맞음, 전제 명시 필요 | 단서 추가 |

## Step 5: 문서 업데이트 제안
FAIL 또는 CONDITIONAL 판정이 있으면:
- 어느 문서의 어느 내용인지 명시
- 수정안을 구체적으로 제시
- 사용자 승인 후 반영

# Mode B: 새 지식 해석 루프

## Step 1: 새 지식 수신
사용자가 제공한 논문, 방법론, 외부 사례를 파악한다.

## Step 2: 판단 기준 먼저 정한다
- 우리 환경(cohort 기반 quasi-experiment)에서 적용 가능한가?
- 기존 원칙(guardrail 우선, Bayesian 해석 등)과 충돌하는가?
- 적용하려면 무엇이 추가로 필요한가?

## Step 3: 갭 점검 (Syneidesis)
TodoWrite로 기록한다:
- `[Gap:Assumption]` 이 지식이 가정하는 환경이 우리와 다른가?
- `[Gap:Procedural]` 적용하려면 현재 없는 데이터/인프라가 필요한가?
- `[Gap:Consideration]` 기존 문서와 충돌하는 내용이 있는가?

## Step 4: 해석 루프 (반복)
새 지식을 단위별로 분해해서 루프를 돌린다:

```
[Unit 1: 핵심 주장]
  → Katalepsis: 이 주장을 우리가 올바르게 이해했는가?
  → Analogia: 이 이론이 우리 실무에 실제로 매핑되는가?
  → Epharmoge: 우리 맥락(cohort 기반, 소규모)에 맞는가?
  → 판정: ADOPT / REJECT / PARTIAL
  → 다음 Unit으로

[Unit 2] → 반복
...
```

**판정 기준:**

| 판정 | 의미 | 후속 조치 |
|------|------|---------|
| **ADOPT** | 수용, 문서에 반영 | 어느 문서에 추가할지 제안 |
| **REJECT** | 우리 환경에 맞지 않음 | 이유 명시 |
| **PARTIAL** | 일부만 수용 | 수용 범위와 조건 명시 |

## Step 5: 문서 반영 제안
ADOPT 또는 PARTIAL이면:
- 어느 문서에 어떻게 추가할지 구체적으로 제시
- 사용자 승인 후 반영

# 출력 형식

```
모드: [기존 지식 검증 / 새 지식 해석]
판단 기준: [명시]
갭: [있으면 목록, 없으면 "없음"]

검증 결과:
  [Claim/Unit 1]: PASS / FAIL / CONDITIONAL / ADOPT / REJECT / PARTIAL
    → [이유 한 줄]
  [Claim/Unit 2]: ...
  ...

후속 조치:
  [문서명]: [수정/추가 내용]
  없음 (모두 PASS/REJECT인 경우)
```

## 다음 단계

- **Mode A (기존 지식 검증)** 완료 후:
  - FAIL/CONDITIONAL 있으면 → 해당 문서 수정 후 `experiment-design` 또는 `validity-check` 재확인
  - 모두 PASS → 원래 하던 Skill로 복귀

- **Mode B (새 지식 해석)** 완료 후:
  - ADOPT → 해당 문서 업데이트 후 `experiment-design`에 반영
  - REJECT → 현재 설계 유지, 원래 Skill로 복귀
  - PARTIAL → 수용 범위 명시 후 `experiment-design`에 조건부 반영
