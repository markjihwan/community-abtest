준실험 트래킹 요건 명세서 (노출·트래픽)

> **📄 요약 ·** 실험데이터 적재 트래킹 요건 명세 — "분모=노출(배정 아님)" 원칙·이벤트/필드 규칙. 두 실험(1차 회고 준실험·2차 사이드바 A/B) 공통이라 `00_common/`에 둠.

작성: K | 2026-06-22 | 수신: L(실험데이터 적재) | 참조: 최지환(프론트 연동)·S(회고 계약)·D(대시보드)

이 문서의 목적. L님의 "실험데이터 적재 작업"이 분석 가능한 형태로 들어오도록, 분석가가 필요한 이벤트·필드·규칙을 미리 정의. 6/28 회고 노출 전에 이 명세대로 적재가 안 되면 트래킹 자체가 불가능하고, 노출이 시작되면 그 이전 상태는 복원할 수 없음. 대상은 1차 회고(준실험), 2차 사이드바(무작위 A/B).

1. ⭐ 가장 중요한 원칙 — 분모는 "노출"이지 "배정"이 아님.
모든 비율 지표(CTR, 전환율, 퍼널 전환)의 분모는 실제로 화면을 본 유저(노출). 배정만 되고 노출이 안 잡히면 모든 수치가 깨질 수 있음.

회고: project_reflection_ui_viewed = 노출
사이드바: exp_exposure = 노출 (가장 중요한 이벤트)
배정됐으나 미노출인 유저는 분석에서 제외. 따라서 노출 이벤트는 반드시 발생·적재되어야 함.
기존 대시보드는 expose 이벤트가 없어 "분모=배정"으로 우회했지만, 이번에 노출 이벤트가 생기면 분모를 노출 기준으로 올릴 것.

5. 적재 규칙 (PLAT-1 event_log)
규칙	내용	왜
멱등(idempotent) 적재	이벤트마다 고유 id, 중복 id 재전송 시 1행만 저장	재전송 시 수치 뻥튀기 방지
Incremental 적재	이벤트는 발생 시 1행 추가하고 끝 (행 단위)	⚠️ event_log를 snapshot(매일 전체 재적재) 방식으로 쌓지 말 것. 회고 현황 리포트에서 snapshot 미필터 시 53배 중복이 확인됐다
base_date 파티션	occurred_at 기준 일자 파티션	기간 필터·증분 처리
PII 마스킹	개인정보는 마스킹 정책 적용	분석 계정은 PII 비접근
상태성 데이터(출석 마트 dm_*)는 snapshot이 맞지만, 행동 이벤트(event_log)는 반드시 incremental이다. 둘을 섞지 말 것.

6. 계측 핵심 규칙 (프론트 연동 시 반드시 — 최지환님)
노출 보장: 배정 ≠ 노출. exp_exposure/viewed가 없는 유저는 분석에서 제외되므로, 화면 렌더 순간 반드시 노출 이벤트를 남긴다.
세션당 노출 1회: sessionStorage 가드로 중복 노출 방지.
클릭-노출 짝: 클릭 이벤트는 같은 variant·session_id의 노출 이벤트와 연결 가능해야 함(orphan 클릭 금지).
Dedup: CTR·전환은 유니크 유저 기준(중복 클릭 1회 처리). 회고 제출은 user_id+experiment_id로 1회.
Variant fallback: 사이드바에서 variant 미수신·오류 시 control로 폴백하고 그 사실을 기록.
7. 적재 후 검증 체크리스트 (K 검수 / QA 게이트)
적재가 시작되면 분석가가 아래를 확인할 것. 하나라도 실패면 트래킹 신뢰 불가.

#	검증 항목	방법	통과 기준
1	노출 이벤트가 실제로 발생	exp_exposure/viewed 행 수 > 0, 배정 대비 노출 비율	노출 누락률 낮음
2	필수 properties null 비율	필드별 null 카운트	필수 필드 null ≈ 0
3	멱등성	같은 event id 재전송 후 행 수	1행 유지
4	클릭-노출 짝	클릭 중 대응 노출 없는 비율(orphan)	orphan ≈ 0
5	incremental 확인	동일 유저·이벤트 중복 폭증 여부	snapshot식 53배 중복 없음
6	variant 비율 (사이드바)	control:treatment 카운트	50:50 근처, SRM χ² p ≥ 0.001
7	조인 키	event_log.user_id ↔ reflection.user_id ↔ dm_member_*	조인 성공
8	회고 제출 키	reflection.experiment_id='s12-mid-reflection' 존재	컬럼·값 적재됨
8. 이 데이터로 분석가가 계산할 것 (필드가 왜 필요한지 역추적)
회고 퍼널: viewed → clicked → submitted 전환율. 세그먼트(user_project_role)·placement_key별 분해.
회고 다운스트림: 작성자 vs 미작성자 출석·완주율 (SMD 균형 후, 자기선택 편향 명시, 연관 등급).
사이드바 CTR: sidebar_item_clicked(projects/events) / exp_exposure, variant별.
사이드바 전환: enrollment_completed / exp_exposure, variant별 + Bayesian P(T>C).
사이드바 Guardrail: 홈 이탈률·세션시간 (page_view·session_start).
SRM: variant 노출 비율 χ² 검정 (scripts/srm_check.py).
9. 노출 시작 시점(6/28 예정) 박제 — 적재 측 협조 필요
회고 노출 전 12기 사전 상태(출석·사전특성)는 노출이 시작되면 사라짐. 분석가가 노트북으로 스냅샷을 박제하되, 적재 측에서 실험 started_at(노출 시작 시각)을 명확히 기록해줘야 cutoff를 맞출 수 있음.

10. 미해결 / 확인 필요
 청강생 구분 — 출석 분석은 정규 멤버만(participant_type='regular'). event_log 또는 조인 가능한 곳에 정규/청강 구분이 들어오나? (회고 현황 리포트: 정규 66.5% vs 청강 74.1%, 섞이면 왜곡)
 SRM 임계값 — 사이드바 글은 χ² p<0.001, 기존 대시보드(memo 10)는 p<0.01. 사이드바 RCT는 p<0.001로 통일 제안. (회고는 준실험이라 SRM 무관)
 user_id 일관성 — event_log / reflection / dm_member_* 출석의 user_id가 같은 체계인가 (canonical).
 K·지환 트래킹 분담 — 둘 다 회의 Action Item이 "준실험(노출, 트래픽) 트래킹". 회고=K / 사이드바=지환, 또는 K=분석 정의·지환=프론트 연동? 경계 확정 필요.
